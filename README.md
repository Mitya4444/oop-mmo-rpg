# Лабораторная по ООП: игровое поле с юнитами

Программа из лабораторной MergeIt: иерархия юнитов, фабрики юнитов и
игровое поле как контейнер со своим итератором. Язык C++, стандарт 17.

## Сборка

Все .cpp лежат в одной папке, собираю так:

    g++ -std=c++17 -Wall -Wextra *.cpp -o lab
    lab.exe

Компилятор g++ (MinGW-w64), терминал VS Code. Точную версию у себя можно
посмотреть командой g++ --version. Сторонних библиотек нет, только std.

## Файлы

- Attributes.h / Attributes.cpp - классы Health, Armor, Attack. Это не
  просто обёртки над int: здоровье не уходит ниже нуля и защищено от
  переполнения, броня срезает урон, атака считает урон через броню цели.
- Unit.h / Unit.cpp - абстрактный юнит. Хранит координаты и три атрибута,
  объявляет чисто виртуальные clone() и getType().
- UnitTypes.h / UnitTypes.cpp - три абстрактных типа (Infantry, Archer,
  Cavalry) и шесть конкретных видов. Характеристики вида зашиты в его
  конструктор.
- UnitFactory.h / UnitFactory.cpp - абстрактная фабрика и три конкретных.
- GameField.h / GameField.cpp - поле: сетка указателей, правило пяти,
  итераторы.
- main.cpp - пять демонстрационных сценариев.

## Почему фабричный метод, а не абстрактная фабрика

Абстрактная фабрика нужна, когда юниты создаются семьями и важно, чтобы
юниты одной семьи были совместимы между собой (условная "армия Севера"
против "армии Юга"). В моём задании такого нет: каждый юнит существует
сам по себе.

При этом по чек-листу нужны три фабрики (пехота, лучники, конница), а видов
в каждом типе два. Без параметра вида трёх фабрик на шесть видов не хватит,
пришлось бы писать фабрику на каждый вид. Поэтому createUnit принимает
параметр UnitKind - это параметризованный фабричный метод, задание само
такую разновидность и предлагает (у него сигнатура createUnit(type, ...)).

Что в паттерне главное: клиент (поле и main) не пишет new Swordsman, он
знает только абстракции UnitFactory и Unit. Добавится новый вид - править
нужно UnitKind и одну фабрику, а не весь код.

## Поле и память

Поле - сетка cells[y][x] из указателей Unit*, пустая клетка это nullptr.
Поле единственный владелец юнитов: delete вызывают только removeUnit, clear
и деструктор поля, каждый юнит удаляется ровно один раз.

- addUnit сначала проверяет границы, свободность клетки и лимит maxUnits,
  и только потом просит юнита у фабрики. Результат фабрики временно живёт
  в unique_ptr: если что-то не подошло, юнит удалится без утечки.
- getUnit возвращает const Unit*: посмотреть можно, удалить юнита в обход
  removeUnit или испортить его через этот указатель нельзя. Урон наносит
  отдельный метод damageUnit.
- Конструктор копирования создаёт новых юнитов через clone(), поэтому копия
  независима от оригинала. Если clone бросит исключение, уже созданные копии
  удаляются в catch, исключение летит дальше.
- Копирующее присваивание по идиоме copy-and-swap: сначала временная копия,
  потом обмен внутренностями. Не удалось скопировать - старое поле не
  тронуто.
- Конструктор и оператор перемещения noexcept, забирают сетку себе, источник
  остаётся пустым, но корректным полем.
- Unit::move меняет собственные координаты юнита; сетка поля сама об этом не
  узнаёт. Поэтому для юнитов, уже размещённых на поле, используется
  GameField::moveUnit: он обновляет и расположение в сетке, и координаты юнита.

## Итератор

Два итератора: GameFieldIterator (даёт Unit&) и ConstGameFieldIterator
(даёт const Unit&). Оба идут по сетке построчно и пропускают пустые клетки,
поэтому снаружи видны только юниты. Есть begin/end и cbegin/cend, значит
range-for работает, в том числе по константному полю. Есть operator*, ->,
++, ==, != и алиасы типов, чтобы итератор понимали стандартные алгоритмы.

Удаление во время обхода в сценарии 5 реализовано через отложенное удаление.
Сначала итератор проходит по полю и собирает координаты юнитов, которые нужно
удалить, в отдельный вектор. После завершения обхода программа удаляет этих
юнитов через removeUnit(). Благодаря этому структура поля не изменяется во
время работы итератора, и не возникает необходимости обращаться к уже
удалённым объектам.

Такой подход требует дополнительной памяти для хранения координат, зато
позволяет безопасно разделить поиск юнитов и их удаление.

## Демонстрации

В main.cpp пять сценариев:
1. Создание поля, наполнение через три фабрики, вывод всех юнитов.
2. Глубокое копирование: урон и удаление в оригинале не трогают копию,
   отдельно проверяется копирующее присваивание и независимость после него.
3. Перемещение: после move источник пуст, владение передано.
4. Обход итератором с массовым уроном всем юнитам.
5. Отложенное удаление: сбор координат во время обхода и удаление после него.
